## Objective

Define the pipeline that turns an upstream provider's own schema output into
pinned Automonique fixtures and a compatibility verdict: capture or generate
the schema bundle for an exact provider binary, hash it, map that digest to the
binary version range it applies to, and classify a diff against the previously
pinned bundle as compatible, breaking, or unclassifiable. An upgrade whose diff
is unclassifiable is not approved by default — it stops.

This slice defines the fixture format, the digest and range mapping, and the
diff classifier as pure functions over supplied schema documents. It invokes no
provider binary, downloads nothing, and enables no adapter version. Capture is
defined here; performing it against an installed binary belongs to the adapter
work in `R2` and is gated on the provider inventory.

## Pipeline contract

- A pinned bundle is checked-in data carrying the provider, the exact binary
  version, the binary digest, the schema document digest with its named
  algorithm, the capture method, and the inclusive binary version range the
  bundle is asserted to cover. A bundle whose digest does not match its
  document fails to load; the two are never trusted independently.
- Digest-to-range mapping is total and non-overlapping per provider: two
  bundles claiming overlapping version ranges for the same provider is a typed
  conflict at load, so a lookup can never silently pick one of two answers.
  A version outside every declared range resolves to an explicit
  `unpinned` outcome rather than the nearest neighbour.
- The classifier compares two schema documents and returns exactly one verdict:
  `compatible` for purely additive change, `breaking` for any removal, type
  narrowing, required-field addition, enum-value removal or semantic
  redefinition, or `unclassifiable` when the diff contains a construct the
  rules do not cover. `unclassifiable` is a first-class outcome and never
  collapses into `compatible`.
- Each verdict carries the specific changed paths that justified it. A verdict
  without evidence is unrepresentable, so a `breaking` result always names what
  broke and a `compatible` result always names what was added.
- Additive change is defined precisely: a new optional field, a new enum value
  in a read-only enum, a new message kind, or a new endpoint. A new enum value
  in a security-sensitive enum is *breaking*, matching the `R1-03` rule that
  such enums reject unknown values — a schema change that would make an
  existing reader fail closed is not compatible merely because it added
  something.
- Classification is deterministic and order-independent: comparing the same two
  documents twice yields identical verdicts and identical evidence paths, and
  the evidence path list is canonically ordered so a diff of two runs is empty.
- The pipeline is offline. Documents are supplied as inputs; no step fetches a
  URL, executes a provider binary or consults a registry.

## Verification contract

| Check | Expected |
|---|---|
| Bundle integrity | a bundle whose document digest does not match its declared digest fails to load; the digest and document are never trusted independently |
| Range mapping | overlapping ranges for one provider are a typed conflict at load; a version outside every range yields an explicit `unpinned` outcome, never a nearest-neighbour guess |
| Verdict exhaustiveness | every diff yields exactly one of `compatible`, `breaking` or `unclassifiable`, proven exhaustive over the classifier's input constructs |
| Unclassifiable is preserved | an unrecognized diff construct yields `unclassifiable` and no path collapses it into `compatible` |
| Evidence completeness | every verdict names the changed paths that justified it; a verdict without evidence is unrepresentable |
| Additive rules | new optional fields, read-only enum values, message kinds and endpoints classify compatible; removals, narrowing, new required fields and enum removals classify breaking |
| Security enum rule | a new value in a security-sensitive enum classifies breaking, consistent with the `R1-03` fail-closed rule |
| Determinism | repeated classification of the same documents yields identical verdicts and canonically ordered identical evidence |
| Offline operation | no step fetches a URL, executes a provider binary or consults a registry |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements, the recorded `R0-06` provider
surface inventory and synthetic schema documents.
`docs/product-plan/requirements/agent-integrations.md` — the Codex requirement
to generate and diff App Server schemas on every upgrade, the opencode
requirement to snapshot and diff the OpenAPI document, and the rule that
conformance is keyed by binary digest, version, integration mode and schema
hash — is the source. Record the verdict distribution over the fixture corpus
and the full classifier rule table with one covering case each. Real captured
provider schemas may be checked in as fixtures only if they were already
captured under `R0-06`; capturing new ones is outside this lease.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a bundle trusted
without digest verification, overlapping ranges resolving silently, an
`unclassifiable` verdict collapsing into `compatible`, a verdict without
evidence paths, a new security-sensitive enum value classified compatible,
non-deterministic or order-dependent classification, any network fetch or
provider execution, a licence-boundary violation, a forbidden clean-room input,
or any path outside the lease.
