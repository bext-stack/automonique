## Objective

Define the workspace registry and artifact vocabulary that keeps host paths out
of the API and content out of the database: registered workspaces with tenant,
canonical source, immutable base revision and snapshot, isolation kind,
writable path token and lock state; and content-addressed artifacts carrying
digest, size, media type, creator, provenance, visibility, retention class and
an abstract storage locator. A run references a workspace revision; it never
receives a host path from a client.

This slice defines the values, the addressing rules and the lock algebra only.
It touches no filesystem, creates no directory, opens no object store, computes
no digest over real bytes and moves no file. What it must make impossible is
that a later layer accepts a caller-supplied absolute path.

## Workspace and artifact contract

- A workspace registration carries tenant, canonical source, immutable base
  revision and snapshot identity, isolation kind, a writable path *token*, lock
  state and lifecycle. The token is an opaque handle resolved by the host; an
  absolute or relative host path is not representable in the registration or in
  any API-facing type, proven by compile-fail coverage.
- A run references exactly one workspace revision. The base revision and
  snapshot are immutable after registration: a mutation attempt is a typed
  error, and producing a changed base means registering a new revision, so
  evidence attached to the old base stays true.
- Locks are exclusive per lock key. Acquiring a held lock yields a typed
  conflict naming the current holder; there is no blocking acquire in the value
  layer and no reentrant acquire that silently succeeds. Release requires the
  holder's identity, so a lock cannot be released by a party that does not hold
  it.
- Artifacts are content-addressed by digest and named algorithm. Identity is
  the digest, not the locator, so the same bytes stored twice are one artifact
  with two locators. A weakened or unknown digest algorithm is rejected at
  construction.
- Every artifact carries tenant, creator, provenance, visibility, retention
  class and an optional encryption key reference. Visibility and retention are
  closed vocabularies with declared defaults; an artifact whose retention class
  is absent is unrepresentable rather than defaulting to "keep forever".
- The storage locator is abstract. A locator names a storage backend and an
  opaque key; it never embeds a filesystem path, a bucket URL with credentials,
  or anything a client could dereference directly. Two locators for one digest
  are permitted; a locator without a digest is not.
- Artifact links bind an artifact to inputs, work, runs, turns, approvals and
  publications as typed relations. A link records its relation kind, so
  "referenced by an approval" is distinguishable from "produced by a run" and
  retention can reason over the difference.
- Deletion is expressible in the documented order — remove access, record a
  tombstone, then permit collection of unreferenced bytes. A tombstone is a
  durable value; cross-tenant deduplication may never prevent a logical
  deletion or reveal that another tenant holds the same bytes.

## Verification contract

| Check | Expected |
|---|---|
| Path unrepresentability | no registration or API-facing type can hold an absolute or relative host path, proven by compile-fail coverage; only opaque tokens are accepted |
| Base immutability | base revision and snapshot cannot be mutated after registration; a mutation attempt is a typed error and a change requires a new revision |
| Lock exclusion | acquiring a held lock yields a conflict naming the holder; no blocking or silently reentrant acquire exists; release requires holder identity |
| Digest addressing | artifact identity is the digest; identical bytes with two locators are one artifact; unknown or weakened algorithms are rejected at construction |
| Required classification | an artifact without a retention class or visibility is unrepresentable; both vocabularies are closed with declared defaults |
| Locator abstraction | a locator cannot embed a filesystem path or a credential-bearing URL; a locator without a digest is unrepresentable |
| Link typing | link relation kinds are distinct and exhaustive over inputs, work, runs, turns, approvals and publications |
| Deletion order | access removal, tombstone and collection are separately expressible in that order; a tombstone is durable and dedup cannot block logical deletion or reveal cross-tenant possession |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

no real file is hashed in this slice.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, any representable
host path in a registration or API type, a mutable base revision, a blocking or
reentrant lock acquire, a release without holder identity, artifact identity
keyed on a locator instead of a digest, a defaulted or absent retention class, a
locator embedding a path or credential, an untyped artifact link, a deletion
path that skips the tombstone, cross-tenant dedup revealing possession, a
filesystem or object-store call, a licence-boundary violation, a forbidden
clean-room input, or any path outside the lease.
