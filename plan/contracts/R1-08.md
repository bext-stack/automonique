## Objective

Define the typed capability model every provider adapter declares and the
negotiation rule that selects an integration mode from it: the capability
groups covering sessions, turns, events, approvals, tools, telemetry and
lifecycle, the `required`/`native`/`degraded` set discipline, and the distinct
provider identities — instance, session, turn, item and request — that must
never be compressed into one opaque string.

This slice defines capability values, identities, negotiation and errors only.
It launches no provider, probes no binary, opens no socket and implements no
adapter. Capabilities are observed at runtime and persisted with a binding;
this layer defines what may be recorded and how a selection decides, not how
the observation is made.

## Capability contract

- Capabilities are a structured value with named groups, not a bag of booleans
  keyed by string. An unrecognized capability name from a newer adapter is
  preserved as an explicitly unknown entry and never counted as present.
  Absence and unknown-ness are distinct; a capability that was never probed is
  not the same as one probed and found missing.
- Each adapter declares three disjoint sets: `required` — Automonique cannot
  safely run without these; `native` — available and tested for this binary and
  protocol; `degraded` — missing in the selected fallback. Overlap between
  `required` and `degraded` for a selected mode is a construction error, since
  it names a mode that is simultaneously mandatory and absent.
- Selection fails closed. A missing required capability refuses the mode with a
  typed error naming every missing capability, and there is no path on which a
  refusal becomes a downgrade. Specifically: an approval-aware protocol is
  never silently replaced by auto-approval, and a resumable session is never
  silently replaced by a fresh run. Both substitutions are separately
  representable as *refusals*, never as outcomes.
- Provider identities are distinct types that do not convert into one another:
  `provider_instance_id` (daemon or socket process identity),
  `provider_session_id` (durable conversation), `provider_turn_id` (one active
  request), `provider_item_id` (tool, message or approval item) and
  `provider_request_id` (protocol correlation). Passing a session where a turn
  is required is a compile error, not a runtime check.
- A session binding is structured over tenant, backend, provider account,
  provider namespace and session ID. An unvalidated opaque session value is
  unrepresentable, so a resume cannot accidentally cross a tenant, account or
  backend boundary. Binding equality compares every component; a partial match
  is a typed mismatch naming the differing component.
- Capability records carry the provider binary version and digest and the
  optional schema digest they were observed against. A capability set is only
  meaningful with those coordinates, so a record missing them cannot be
  constructed and a stale record is detectable by digest comparison alone.
- Degradation is declared, visible and job-scoped. The value layer exposes the
  degraded set so a client can display it and a policy can reject jobs
  requiring an absent capability; it never decides on its own that a
  degradation is acceptable.

## Verification contract

| Check | Expected |
|---|---|
| Capability structure | unknown capability names from a newer adapter round-trip as explicitly unknown and never count as present; unprobed and probed-absent are distinguishable |
| Set discipline | `required`, `native` and `degraded` are disjoint as declared; a mode whose required set intersects its degraded set fails at construction |
| Fail-closed selection | a missing required capability refuses with a typed error naming every missing capability; no path converts a refusal into a downgrade |
| Forbidden substitutions | approval-aware to auto-approval, and resumable-session to fresh-run, are each representable only as refusals, proven by exhaustive selection tests |
| Identity distinctness | instance, session, turn, item and request identities do not interconvert, proven by compile-fail coverage |
| Binding safety | an unvalidated opaque session value is unrepresentable; equality compares every component and a partial match names the differing component |
| Cross-boundary resume | a binding differing in tenant, backend, provider account or namespace is refused with the component named |
| Provenance completeness | a capability record without binary version and digest cannot be constructed; a stale record is detectable by digest comparison |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements, the recorded `R0-06` provider
surface inventory and synthetic fixtures.
`docs/product-plan/requirements/agent-integrations.md` § Common capability
model and § Distinct identities are the sources for the capability groups, the
three-set discipline and the identity list. Record the capability-group
coverage table, the selection case matrix and every refusal category. Do not
probe an installed provider binary in this slice; a capability asserted from a
live CLI rather than the inventory is unmeasured for this contract.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a capability
model keyed by unbounded strings, unknown capabilities counting as present, any
path where a missing required capability yields a downgrade instead of a
refusal, interconvertible provider identities, a representable unvalidated
opaque session value, a binding comparison that ignores a component, a
capability record constructible without binary provenance, a provider launch or
probe, a licence-boundary violation, a forbidden clean-room input, or any path
outside the lease.
