## Objective

Define the sandbox vocabulary every execution decision is compiled into:
versioned profiles as minimum contracts, the immutable `SandboxSpec` referenced
by a `RunSpec`, the `EnforcementAttestation` a host records before provider
input, the violation and quarantine outcomes, resource and storage budgets, the
strictly separated provider-control and tool-workload egress policies, and the
negotiation that fails closed when a required enforcement feature is absent.

This slice defines values, comparison and negotiation only. It creates no
namespace, loads no seccomp filter, applies no Landlock ruleset, allocates no
cgroup and launches nothing. It must nonetheless make the dangerous states
unrepresentable, because a boundary defined loosely here is a boundary that
`R2` cannot enforce tightly.

## Sandbox contract

- A profile is versioned and is a *minimum* contract. A deployment may narrow
  it; adding a capability requires a new plan revision. Profile comparison is a
  typed partial order returning `narrower`, `identical`, `wider` or
  `incomparable` — never a boolean — so "is this safe to reuse" is answered by
  the type rather than by a caller's convention.
- The `SandboxSpec` is immutable once compiled and carries profile identity and
  version, complete policy digest, tenant, actor, provider account and
  workspace security-context hash, immutable base revision, readable and
  writable path grants, executable/interpreter/tool/MCP/companion allowlists,
  the two distinct network policies, credential descriptors with the exact
  process class allowed to receive each, cgroup/rlimit/timeout/temporary
  storage/spool/artifact budgets, required kernel and backend features with
  accepted enforcement implementation digests, nested isolation requirements,
  and the approval/policy revision plus prohibited-capability set.
- There is no silent downgrade. A missing required enforcement feature is a
  refusal that names the feature; no path resolves a stronger profile into a
  weaker one, and the absence of a fallback path is proven by exhaustive
  negotiation tests rather than asserted.
- The provider-control network policy and the tool-workload network policy are
  distinct types that cannot be substituted for one another. A spec carrying
  one where the other is required does not compile. Collapsing them is the
  failure mode that lets model-directed traffic inherit control-plane reach.
- An `EnforcementAttestation` records resolved real paths, namespaces,
  process-group, cgroup and backend identities, kernel and boot identity,
  effective optional-supervisor properties, Landlock ABI and ruleset digest,
  seccomp digest, egress-policy digest, credential delivery mode and any
  verified external-daemon context. Attestation is compared, not reconstructed:
  reload adoption compares digests against the recorded attestation, and a
  missing or mismatched object yields `quarantined`, which permits only bounded
  observation, reconciliation or cancellation.
- Session reuse requires the new request to be identical or demonstrably
  narrower across tenant, provider account, workspace context, credentials and
  policy. Any widening produces a new revision, expressed as a typed
  `requires_new_host` outcome rather than an in-place mutation.
- A provider approval request can never widen a `SandboxSpec`. The approval
  types have no path that returns a modified spec — added authority yields a
  new reviewed plan — and this is proven by compile-fail coverage.
- Budgets are typed quantities with declared units and ceilings. A budget
  without a unit, or exceeding its declared ceiling, is unrepresentable, and
  exhaustion is a distinct outcome from violation.
- Violations are classified — policy violation, budget exhaustion, enforcement
  loss, attestation mismatch — and each maps to a declared disposition. A
  violation never resolves to "continue".

## Verification contract

| Check | Expected |
|---|---|
| Profile ordering | comparison returns `narrower`, `identical`, `wider` or `incomparable`, never a boolean; `incomparable` is reachable and preserved |
| Spec immutability and completeness | a compiled `SandboxSpec` cannot be mutated; every listed field is required, proven by a coverage table against the requirement |
| No silent downgrade | a missing required enforcement feature refuses naming the feature; exhaustive negotiation tests prove no stronger-to-weaker resolution path exists |
| Egress split | provider-control and tool-workload policies do not substitute for one another, proven by compile-fail coverage |
| Attestation comparison | reload adoption compares recorded attestation digests; a missing or mismatched object yields `quarantined` permitting only observation, reconciliation or cancellation |
| Narrowing-only reuse | identical or narrower requests may reuse a host; any widening yields `requires_new_host` rather than in-place mutation |
| Approval cannot widen | no approval path returns a modified spec, proven by compile-fail coverage |
| Budget typing | budgets carry declared units and ceilings; unitless or over-ceiling budgets are unrepresentable; exhaustion and violation are distinct outcomes |
| Violation dispositions | every violation class maps to a declared disposition and none resolves to "continue" |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements and synthetic fixtures.
`docs/product-plan/requirements/sandbox-management.md` § Policy compilation,
§ Standard profiles, § Provider, MCP and extension containment and § Session
reuse and reload are the sources for the spec field list, the no-silent-fallback
rule, the egress split and the quarantine behavior. Record the profile
comparison matrix, the negotiation refusal table and the compile-fail cases for
the egress split and the approval-cannot-widen rule. This slice defines the
boundary; it does not prove enforcement, and evidence must say so rather than
implying a kernel property was tested.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a mutable
compiled spec, a boolean profile comparison, any path resolving a stronger
profile to a weaker one, substitutable network policies, an attestation
reconstructed rather than compared, host reuse under a widened request, an
approval path that returns a modified spec, an unitless or uncapped budget, a
violation class with no disposition or one that continues, an enforcement claim
this layer cannot support, a licence-boundary violation, a forbidden clean-room
input, or any path outside the lease.
