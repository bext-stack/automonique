## Objective

Define the vocabulary for choosing a model, handling media and admitting an
execution backend: the normalized model and provider catalog, durable
explainable routing decisions, credential pools bounded by billing tenant and
data boundary, mixture-of-agents reference outputs that are structurally
untrusted, media adapter declarations with provenance and retention, and the
execution-provider registration whose lifecycle evidence must be fenced rather
than asserted by a vendor label.

This slice defines catalog, policy, decision and registration values only. It
calls no model, transcodes no media, allocates no worker, contacts no vendor and
takes no screenshot. Its central obligation is that no routing or fallback path
can silently cross a sovereignty, billing or provider-account boundary.

## Model, media and executor contract

- A catalog entry declares models, modalities, context and output limits,
  reasoning controls, tool and structured-output support, region and data
  policy, pricing and auth method. Model aliases are versioned profile data,
  not global mutable state, so resolving an alias is reproducible at a
  recorded revision.
- A routing decision is durable and explainable: it records the ordered
  candidates considered, the constraint that eliminated each rejected one, and
  the selected provider account. A decision without its rejection reasons is
  unrepresentable, so "why did this run on that model" is always answerable.
- A mid-session model switch is a new turn revision carrying its cache and
  context consequences. Crossing a sovereignty boundary or a provider account
  is a typed refusal rather than a switch, and a session-bound provider cannot
  migrate mid-session merely because another model is healthy.
- Credential pools group provider accounts that explicitly share tenant,
  billing and data-boundary policy. Rotation is expressible only within one
  pool; a rotation type spanning two pools does not compile. Usage and
  exhaustion are observable without any secret value being representable.
- Fallback chains are declared independently for primary turns and for each
  auxiliary class — titling, compression, memory review, vision, transcription,
  speech and evaluation. A fallback preserves the requested tools, sandbox,
  residency and approval semantics; a chain whose next hop weakens any of them
  is rejected at construction, not at dispatch.
- Mixture-of-agents reference outputs are labelled untrusted advice by
  construction: they carry a minimized context, hold no tools, and have no path
  to approve an action or to be promoted into an authoritative record. Only the
  acting aggregator produces a result. Every reference call is a first-class
  usage record counted against tenant budgets.
- Media adapters declare supported formats, content limits, model and version,
  cost, retention and data policy, credential and egress. Generated and derived
  media enters the artifact service from `R1-14` with provenance; a platform
  derivative is a distinct artifact from the protected original. Spoken
  confirmation is not privileged approval — a voice input type that satisfies an
  approval requirement is unrepresentable — and wake-word detection grants no
  authority.
- Browser and computer-use records carry the reviewed origin allowlist, capture
  policy, isolation identity and sandbox attestation from `R1-18`. Downloads
  are quarantined artifacts. Native OS access is never inferable from a browser
  grant: the two capabilities are distinct types with no conversion.
- An executor registration declares its class — local, container, SSH, batch,
  cluster, microVM or remote — and must carry workspace and artifact transfer,
  immutable spec acceptance, sandbox attestation, credential handling, event
  cursor, approval pause, cancellation, cleanup and cost accounting. Every
  field is required, so no backend is registrable merely because it can execute
  a command. Lifecycle evidence must be signed or mutually authenticated; a
  vendor's "sandbox" label is not an accepted attestation and is unrepresentable
  as one. Remote vendor identifiers are coordinates, never authority.
- A persistent remote environment carries identity, snapshot and hibernation
  state, and scale-to-zero is a distinct state from a running process.

## Verification contract

| Check | Expected |
|---|---|
| Catalog completeness | every declared catalog field is required; alias resolution is reproducible at a recorded revision |
| Explainable routing | a decision records ordered candidates and the constraint eliminating each rejection; a decision without rejection reasons is unrepresentable |
| Boundary refusals | a mid-session switch crossing sovereignty or provider account is a typed refusal; a session-bound provider cannot migrate for health alone |
| Pool containment | rotation across two pools does not compile; usage and exhaustion are observable with no representable secret value |
| Fallback preservation | a chain whose next hop weakens tools, sandbox, residency or approval semantics is rejected at construction |
| Untrusted advice | reference outputs carry minimized context, hold no tools, cannot approve, and have no promotion path to an authoritative record; each is a counted usage record |
| Media provenance | derived media carries provenance and is a distinct artifact from the protected original; declared adapter fields are required |
| Voice is not approval | a voice input satisfying an approval requirement is unrepresentable, and wake-word detection grants no authority |
| Capability separation | native OS access cannot be derived from a browser grant; the two are distinct types with no conversion; downloads are quarantined artifacts |
| Executor completeness | every executor field is required; unsigned or vendor-labelled attestation is unrepresentable; remote identifiers carry no authority; scale-to-zero is distinct from running |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements and synthetic fixtures.
`docs/product-plan/requirements/models-media-and-execution.md` § Model and
provider catalog, § Routing, fallback and credential pools, § Mixture of agents
and auxiliary models, § Media capabilities, § Web, browser and computer use and
§ Execution-provider SPI, together with
`docs/product-plan/requirements/state-and-protocols.md` § Public protocols,
media and execution backends, are the sources. Record the routing decision case
matrix with its rejection reasons, the boundary-refusal table, and the
compile-fail cases for cross-pool rotation, voice approval and browser-to-OS
capability conversion. No model, vendor or media backend is contacted; a test
that contacts one has left the lease.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a routing decision
without rejection reasons, a silent cross-sovereignty or cross-account switch, a
session-bound provider migrating for health, rotation spanning pools, a
representable secret value, a fallback that weakens tools, sandbox, residency or
approval, a reference output that can approve or be promoted, derived media
without provenance, a voice input satisfying an approval, native OS access
derivable from a browser grant, an executor registrable without full lifecycle
evidence, a vendor label accepted as attestation, a network or vendor call, a
licence-boundary violation, a forbidden clean-room input, or any path outside
the lease.
