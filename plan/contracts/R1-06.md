## Objective

Build the shared fixture corpus and the two-direction conformance harness that
proves the Rust and TypeScript protocol implementations agree exactly: Bun
encodes and Rust decodes, Rust encodes and Bun decodes, and both directions
produce byte-identical frames and identically classified rejections for every
fixture. A cross-language claim that rests on one direction only proves the
encoder and decoder share a bug.

This slice defines the corpus, the harness and the agreement rules. It adds no
new protocol semantics: a fixture that cannot be expressed with the primitives
and codec already landed by `R1-02` and `R1-03` is out of scope, and widening
either to make a fixture pass is forbidden.

## Fixture contract

- Fixtures are checked-in data, not generated at test time. Each carries a
  stable identifier, the canonical encoded bytes as an explicit hex or base64
  literal, the decoded logical value, and an expected outcome that is either
  `accept` or a named rejection category.
- Every fixture runs in both directions. Rust-encode/Bun-decode and
  Bun-encode/Rust-decode are separate recorded results; a corpus where one
  direction is skipped, xfailed or unimplemented does not support a parity
  claim, and the evidence records per-direction counts rather than a total.
- Agreement is byte-for-byte on the encoded frame, not structural equality
  after re-decoding. Both implementations must produce the same canonical
  ordering, the same integer and string encodings and the same treatment of
  absent versus null fields.
- Rejection parity is required and is stated per category: a fixture expected
  to fail must fail in both languages *with the same error category*. Failing
  for different reasons is a mismatch, because it means one side accepted a
  frame the other rejected for an unrelated cause.
- The corpus covers, at minimum: exact-limit and one-byte-over frames, empty
  and maximal payloads, multibyte UTF-8 at a byte boundary, maximum nesting
  depth and one level beyond, unknown additive fields, unknown
  security-sensitive enum values, unknown read-only enum values, unsupported
  major versions, unknown protocol names, and every `R1-02` primitive at its
  exact and over-limit bound.
- The harness runs offline with no network access and no installed daemon. It
  reports a per-fixture, per-direction result table; a run that cannot execute
  one direction reports that as an explicit gap, never as a pass.
- Rust schemas are the wire source of truth. When the two disagree, the fixture
  records which side was wrong and the fix goes to the implementation, never to
  the fixture. A fixture edited to match observed behavior is a regression that
  scores well, which is exactly what `plan/doctrine.md` forbids.

## Verification contract

| Check | Expected |
|---|---|
| Both directions run | every fixture produces a recorded Rust-encode/Bun-decode and Bun-encode/Rust-decode result; skipped, xfailed or unimplemented directions are counted as gaps, never passes |
| Byte agreement | encoded frames match byte-for-byte across languages, including field ordering, integer and string encoding, and absent-versus-null treatment |
| Rejection parity | every rejecting fixture fails in both languages with the same error category; differing categories are reported as mismatches |
| Boundary coverage | exact-limit, one-byte-over, empty, maximal, multibyte-UTF-8-at-boundary and maximum-plus-one nesting fixtures are present and pass |
| Compatibility tolerance | unknown additive fields decode; unknown security-sensitive enum values reject; unknown read-only values decode to `unknown` identically in both languages |
| Negotiation coverage | unknown protocol names and unsupported major versions reject identically in both languages |
| Offline execution | the harness runs with no network access and no installed daemon, and a missing runtime is reported as a gap rather than a pass |
| Licence split | TypeScript fixtures and harness code under `sdk/` carry `Apache-2.0`; Rust-side code carries `Elastic-2.0`; the split is recorded |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements, the structural migration map and
synthetic fixtures. `docs/product-plan/requirements/typescript-sdk.md` is the
source for the zero-diff regeneration rule and the requirement that a released
SDK records its exact schema digest and protocol range. Record per-fixture,
per-direction accept and reject counts, the error-category agreement table, and
the exact Bun and Rust toolchain versions the run used. An unavailable Bun
runtime makes the cross-language claim unmeasured — record it as `null` with a
reason, never as a pass.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a fixture edited
to match observed behavior rather than the specification, a direction that is
skipped or reported as passing without executing, structural comparison
substituted for byte comparison, rejection parity claimed without matching
error categories, a fixture generated at test time by the implementation under
test, a network or daemon dependency, a licence-boundary violation, a forbidden
clean-room input, or any path outside the lease.
