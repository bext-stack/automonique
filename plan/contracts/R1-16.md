## Objective

Define the platform-neutral connector vocabulary that lets Teams, Discord and
future channel bridges reach Automonique without leaking their own types into
the core protocol: installation-to-tenant resolution, external-identity-to-actor
mapping with an explicit unlinked state, stable source keys, durable input
submission, outbound render intents, opaque action tokens bound to an exact
target revision, and the artifact grants that replace direct file access.

This slice defines the connector-facing values, the resolution rules and the
conformance obligations only. It speaks to no platform, verifies no webhook
signature, holds no bot token, renders no card and sends no message.
Platform-specific Activity, Adaptive Card, Interaction and Component types are
explicitly *not* representable here — that is the boundary this contract exists
to hold.

## Connector contract

- Installation resolution maps exactly one platform installation — platform
  application identity plus external tenant, guild or installation owner — to
  exactly one Automonique tenant. There is no global fallback tenant and no
  default: an unrecognized installation resolves to a typed
  `installation_required` outcome, never to a permissive default.
- External identity resolves to a durable actor or to an explicit `unlinked`
  state. `unlinked` is a first-class outcome carrying what is needed to prompt
  linking; it is never an error swallowed into an anonymous actor. Display
  names, email addresses, usernames and mutable handles are attributes and are
  rejected as authorization identifiers, consistent with `R1-13`.
- A source key is stable and deterministic over platform, installation and the
  platform's own immutable event or message identity. The same platform event
  yields the same source key across restarts and connector instances, so
  duplicate delivery is detectable without coordination. Source keys never
  incorporate a timestamp, a random value or a connector process identity.
- Platform acknowledgement and business acceptance are separate outcomes. A
  connector may acknowledge immediately, but `accepted` is expressible only
  once a durable input identity exists. The two are distinct types so an
  acknowledgement cannot be returned where an acceptance is required.
- Outbound communication is expressed as a render *intent* — a typed
  progress, clarification, approval or terminal record — never as a
  platform-specific model string or pre-rendered markup. Intents are derived
  from durable Automonique events, so a connector cannot invent state a
  platform user then believes.
- Every interactive control binds to an opaque action token carrying the exact
  target revision and the eligible actor policy. The token is opaque to the
  platform, the stored form is a hash, and resolving a token against a changed
  target revision is a typed conflict rather than a re-targeted action. An
  expired token is a distinct outcome from an unauthorized one.
- Attachments move only through artifact grants. A connector receives a bounded
  upload or download grant; a filesystem path, a platform CDN URL bearing
  credentials and an unbounded byte payload are all unrepresentable.
- Conversation coordinates — platform, installation, conversation scope,
  thread or reply key, message or interaction identity, locale and mention
  context — are preserved as typed values. Edited messages produce a revision
  event and deleted messages produce a tombstone; neither rewrites an already
  approved action or erases an audit record.
- The conformance obligations are declared as a checkable list so a connector
  can be judged against the same contract regardless of platform, including
  restart resumption without replaying an external effect.

## Verification contract

| Check | Expected |
|---|---|
| Installation resolution | one installation resolves to one tenant; an unrecognized installation yields `installation_required`; no global fallback tenant is representable |
| Identity resolution | external identity resolves to an actor or an explicit `unlinked` state; mutable handles are rejected as authorization identifiers |
| Source-key stability | the same platform event yields the same key across restarts and instances; timestamps, randomness and process identity cannot enter a key |
| Acknowledgement split | acknowledgement and business acceptance are distinct types; `accepted` requires a durable input identity |
| Render intents | outbound content is a typed intent derived from durable events; a platform-specific model string or pre-rendered markup is unrepresentable |
| Action-token binding | tokens are opaque, stored hashed, and carry target revision and eligible actor; a changed target revision yields a conflict; expiry and unauthorized are distinct outcomes |
| Artifact grants | attachments move only through bounded grants; filesystem paths, credential-bearing URLs and unbounded payloads are unrepresentable |
| Coordinate preservation | platform, installation, conversation, thread, message, locale and mention coordinates round-trip; edits produce revisions and deletions produce tombstones without rewriting approved actions |
| Platform-type isolation | no Teams Activity/Adaptive Card or Discord Interaction/Component type is representable in the core protocol, proven by the crate's public surface |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements and synthetic fixtures.
`docs/product-plan/requirements/channel-integrations.md` § Common connector
contract, § Installations and tenancy and § TypeScript SDK connector surface,
plus `docs/product-plan/requirements/state-and-protocols.md` § External
connector installations and conversations, are the sources. Record the
resolution outcome matrix, the source-key stability property-test results and
the conformance obligation table. Fixtures use fake tenants and guilds only; no
real tenant, guild, team, channel or user identifier appears anywhere, and
`GATE-SCRUB` treats a real one as a scan failure.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a representable
global fallback tenant, an unlinked identity collapsing into an anonymous
actor, a mutable handle used for authorization, a source key incorporating time
or randomness, acknowledgement standing in for acceptance, a platform-specific
type reaching the core protocol, an action token that survives a target
revision change, an attachment path or credential-bearing URL becoming
representable, a deletion that erases an audit record, a real tenant or guild
identifier in a fixture, a network call, a licence-boundary violation, a
forbidden clean-room input, or any path outside the lease.
