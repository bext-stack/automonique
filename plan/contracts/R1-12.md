## Objective

Define the journal vocabulary that makes every authoritative state change
resumable and explainable: schema-versioned domain events with globally ordered
identifiers, per-aggregate revisions, action receipts keyed by idempotency key,
durable consumer cursors by consumer identity and topic, and a replay operation
whose API confers no effect capability. Replay may rebuild a projection or
explain history; it hands the projection nothing the projection did not already
own. Projection-owned handles remain limit L1 below.

This slice defines the event and action value types, revision and cursor
algebra, and the replay signature that grants no effect capability. It opens no
database, runs no transaction, writes no row and delivers
no outbox message. Event schema versioning here is independent of table schema,
and this contract owns only the former.

## Journal contract

- A domain event carries a globally ordered event identifier, its aggregate
  identity and the aggregate revision it produced, an event schema version, an
  occurrence timestamp and a bounded typed payload. Event schemas are versioned
  independently of database schema, so a reader declares an event decode range
  separately from its `[min_schema, max_schema]` table range.
- Event identifiers are strictly increasing across the whole journal.
  Per-aggregate revisions are strictly increasing within their aggregate and
  begin at the first revision, reusing the non-zero revision primitive from
  `R1-02`. Appending an event whose revision is not the exact successor of the
  aggregate's current revision is a typed conflict carrying both the expected
  and the observed revision.
- An action receipt records the action identity, the typed target, the expected
  revision the caller asserted, the idempotency key, and a terminal outcome
  drawn from a closed set: `accepted`, `completed`, `rejected`, `conflict`,
  `unknown` or `resync_required`. Transport failure and operation failure are
  distinct outcomes and a caller cannot confuse them.
- Idempotency is exact: replaying an action with the same key and the same
  target yields the identical recorded receipt. The same key with a *different*
  target or payload is a typed conflict, not an overwrite and not a second
  execution. A receipt is queryable after the requesting client has
  disconnected, so a receipt type that borrows from a live connection is
  unrepresentable.
- Consumer cursors are durable, keyed by consumer identity and topic, and
  advance monotonically. A cursor outside the resumable window
  `first ..= caught_up`, where `caught_up` is `last.saturating_add(1)`, yields
  `resync_required` with bounded snapshot coordinates. A cursor may not move
  backwards, and an attempt to do so is a typed error rather than a silent
  rewind. See A2 and limit L2.
- Replay grants no effect capability by type rather than by convention: the
  entry point takes a projection and nothing else, and no outbox, notification,
  transport or effect handle can be obtained from this crate inside it. It does
  not make a projection pure; see A1 and limit L1.
- Every authoritative transition and accepted mutation is expected to commit
  its journal row in the same transaction as its effect. This slice cannot
  enforce transactionality — it has no store — so it defines the types that
  make the paired write expressible and records that the enforcement belongs to
  `R4`.

## Verification contract

| Check | Expected |
|---|---|
| Global ordering | event identifiers are strictly increasing across the journal; a duplicate or out-of-order append is a typed error |
| Revision algebra | per-aggregate revisions start at the first revision and increase by exactly one; a non-successor append is a conflict naming expected and observed |
| Schema independence | event decode ranges are declarable independently of table schema ranges, and an out-of-range event version fails closed |
| Outcome vocabulary | the receipt outcome set is closed and exhaustive; transport failure and operation failure are distinct and cannot be conflated |
| Idempotency exactness | the same key and target replay to the identical receipt; the same key with a different target or payload is a typed conflict |
| Receipt durability | a receipt is queryable after client disconnect; a receipt type borrowing from a live connection does not compile |
| Cursor monotonicity | cursors advance only forward; a backwards move is a typed error; a cursor outside the resumable window `first ..= caught_up`, where `caught_up = last.saturating_add(1)`, yields `resync_required` with bounded snapshot coordinates — see A2 and limit L2 |
| Replay purity | replay confers no effect capability: paired positive/negative cases cover replay arity and callback signatures; compile-fail cases cover the named field/default construction routes; API inspection confirms no other exported `Outbox` constructor — see A1 and limit L1 |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Amendments

Accepted by the owner on 2026-08-12 and applied above. Two rules shape the
recorded form.

`AGENTS.md`: *a candidate is judged by those rules as they stand at its own
admitted base, never by the version it introduces.* The implementation
candidate that discovered these amendments did not use them to close its own
row. The superseded wording remains quoted below, while the accepted wording is
now the rule that judges later R1-12 attempts.

`plan/doctrine.md`: *never resolve a contradiction by deleting one side.* An
amendment that lowered a bar to match the code, with the difference quietly
dropped, would be the failure this file exists to prevent. Each amendment below
therefore quotes what it supersedes, says what cannot be met and why, and names
the residual it leaves as a numbered limit that a later item can be held to.

### A1 — Replay purity: state the boundary that exists; name the residual

Superseded — row `Replay purity`:

> no effect, outbox, notification or transport handle is reachable inside
> replay, proven by compile-fail coverage

and § Journal contract, replay bullet:

> Replay is side-effect-free by type, not by convention: the replay entry point
> accepts only a pure projection function and there is no way to reach an
> outbox, notification, transport or effect handle from inside it.

**Why no implementation can satisfy it.** A projection owns its fields, so a
projection constructed holding a channel, socket or file handle reaches that
handle inside `apply`, having brought it rather than been given it. Measured,
not argued: a projection whose own field is an `std::sync::mpsc::Sender`, and
whose `apply` calls `std::fs::write`, compiles against the built rlib and both
effects happen inside `Journal::replay`. No signature can prevent this, because
Rust has no effect system: "the argument list contains no handle" and "the
callee performs no effect" are different claims, and only the first is a type.
The words "accepts only a pure projection function" name a thing Rust cannot
express.

**Amended row wording.** Replay confers no effect capability. Paired positive
and negative cases cover replay arity and callback signatures; compile-fail
cases cover the named private-field and `Default` construction routes; API
inspection confirms there is no other exported `Outbox` constructor. Together:
replay hands a projection nothing it did not already own. Limit L1 is out of
the proof's scope and is demonstrated by a test rather than asserted away.

**Amended § Journal contract bullet.** Replay grants no effect capability by
type rather than by convention: the entry point takes a projection and nothing
else, and no outbox, notification, transport or effect handle can be obtained
from this crate inside it. It does not make a projection pure — see L1.

**Amended stop condition.** "Any reachable effect inside replay" is met by
every projection that owns a handle and so cannot be a stop condition as
written; it becomes *any effect handle obtainable from this crate's API inside
replay*.

> **Limit L1 — projection-owned handles.** A projection can smuggle in its own
> handle. This is a discipline, not a guarantee. It is irreducible in safe Rust
> and will stay irreducible for every callback interface this crate defines.
> What would actually close it is not a signature: an effect system the
> language does not have, or moving the enforcement to a boundary that can deny
> a syscall — the process or sandbox boundary modelled elsewhere in this
> workspace. Until then the property is a review obligation on whoever
> constructs the projection, and it is written down here so that a later item
> that claims replay purity has to say which of those two it did.

### A2 — Cursor monotonicity: "outside the retained range" is off by one

Superseded — row `Cursor monotonicity`:

> an out-of-range cursor yields `resync_required` with snapshot coordinates

and § Journal contract, cursor bullet:

> A cursor outside the retained range yields `resync_required` with bounded
> snapshot coordinates.

**Why it cannot be met literally.** A cursor names the boundary *before* the
next position its consumer will receive, not an event. For a window
`first ..= last` whose `last` is below `u64::MAX`, there are therefore
`last - first + 2` resumable cursor positions — one more than the window
retains — so the resumable set cannot coincide with the retained set. At
`u64::MAX`, `caught_up` saturates and there is no representable extra position.
Read literally, an ordinary consumer whose window ends below `u64::MAX` sits at
`last + 1`, is told to resync, takes a
snapshot covering through `last`, returns to `last + 1`, and is told to resync
again: the literal reading livelocks the ordinary caught-up state.

**Amended row wording.** Cursors advance only forward; a backwards move is a
typed error; a cursor outside the *resumable* window `first ..= caught_up`,
where `caught_up = last.saturating_add(1)`, yields `resync_required` with
bounded snapshot coordinates — below that window and above it alike.

**What that costs and what it buys.** It concedes exactly one position, L2. It
also closes a hole the previous reading left open in the other direction: under
"outside means below", every position above the window resumed live, so a
cursor left ahead of a truncated or rebuilt topic was served live delivery
starting at a position the topic had not reached, silently skipping everything
written between `last + 1` and the cursor. The amended window classifies that
as `resync_required`, which is a behaviour change and is disclosed as one in
the evidence rather than folded in.

> **Limit L2 — the caught-up position.** When `last < u64::MAX`, exactly one
> position, `caught_up = last + 1`, is outside the retained window and is
> nonetheless live. At `u64::MAX`, `caught_up` saturates to `last`. It is a
> boundary rather than an event, and nothing is skipped by serving it. Any future statement
> about cursors and retention has to be written in the resumable window
> `first ..= last + 1`, never in the retained window, or it will be off by one
> again.

Not in scope of A2, and recorded rather than fixed: `event::resolve_subscription`
applies the superseded "below only" rule to the parallel cursor type in
`src/event.rs`, so it carries the above-window hole this amendment closes here.
That file is outside this item's lease. The duplication of
`JournalCursor`/`RetainedRange` against `ConsumerCursor`/`resolve_subscription`
is the underlying defect and neither is fixable from inside R1-12's lease.

## Compatibility and evidence

Use only the permitted product requirements, the structural migration map and
synthetic fixtures.
`docs/product-plan/requirements/state-and-protocols.md` § Domain events and
action receipts and § Database migration compatibility are the sources for
global resumability, the cursor rule and the independence of event and table
schema versioning. Record the conflict and outcome category tables, the
replay-purity compile-fail cases, and the property-test case counts for
ordering and idempotency. Table-level transactionality is out of lease and is
recorded as deferred to `R4` rather than claimed here.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, non-monotonic
event identifiers or revisions, a revision conflict resolved by overwrite, an
open-ended outcome vocabulary, transport and operation failure collapsing into
one outcome, an idempotency key accepting a changed target, a receipt that
cannot outlive its client, a cursor that can move backwards, any effect handle
obtainable from this crate's API inside replay, a database or transport call, a
licence-boundary violation, a forbidden clean-room input, or any path outside
the lease.
