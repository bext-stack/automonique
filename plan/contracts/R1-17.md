## Objective

Define the single name registry from which both the canonical Automonique name
and every legacy forwarding alias are generated, together with the rules that
reject a configuration naming both, and the mechanical proof that a canonical
name and its aliases resolve to exactly one runtime owner and one durable
identity. Two spellings of a setting must never become two sources of truth.

This slice defines the registry, the generator's output contract and the
conflict rules. It renames no durable identifier, migrates no data, forwards no
live request and rewrites no existing configuration. A durable identifier is
never rewritten for branding — the compatibility surface exists so that it does
not have to be.

## Registry contract

- One registry entry declares the canonical Automonique name, its zero or more
  legacy aliases, the identifier class — environment variable, command,
  configuration key, protocol name, schema name, metric, tracing target or
  route — and its compatibility disposition. Both the canonical name and its
  aliases are *generated* from that entry; a hand-written alias that is not in
  the registry is a build failure, not a convenience.
- Aliases are forwarding or codec boundaries only. An alias may translate a
  name and may decode a version-1 wire shape; it may not carry behavior the
  canonical path does not have. Duplicate domain behavior behind an alias is
  the specific failure this contract exists to prevent.
- Configuration resolution rejects conflict rather than choosing. If both a
  canonical key and one of its aliases are set, resolution fails with a typed
  conflict naming both spellings and their values — it never applies a
  precedence rule, because a precedence rule is how one of two configured
  values silently wins for a year.
- Setting an alias alone succeeds and records a deprecation observation
  carrying the canonical name to migrate to. The observation is a value, not a
  log line, so a client can surface it and an operator can enumerate every
  alias still in use.
- One-owner resolution is mechanical: for every registry entry, the canonical
  name and each alias resolve to the same runtime owner and the same durable
  identity. This is proven by a generated table covering every entry, not by
  spot checks, and an entry resolving to two owners fails the build.
- Every alias declares an explicit compatibility window and the migration
  contract that authorizes it. An alias with no authorizing contract cannot be
  added, matching the standing rule against renaming durable identifiers or
  compatibility surfaces without one.
- Legacy identifiers appear in the registry and in
  `docs/product-plan/reference/legacy-inventory.md`, and nowhere else. The
  generator emits them into code from the registry; prose elsewhere uses the
  neutral description, and a legacy identifier appearing outside those two
  places is a `GATE-SCRUB` failure even though it is permitted inside them.

## Verification contract

| Check | Expected |
|---|---|
| Single source | canonical names and aliases are generated from one registry; a hand-written alias absent from the registry fails the build |
| Forwarding only | an alias carrying behavior the canonical path lacks is rejected; aliases are provably forwarding or codec boundaries |
| Conflict rejection | setting both a canonical key and its alias fails with a typed conflict naming both spellings and values; no precedence rule exists |
| Deprecation observation | setting an alias alone succeeds and yields an enumerable observation carrying the canonical name |
| One owner | a generated table proves every canonical name and each of its aliases resolve to one runtime owner and one durable identity; a two-owner entry fails the build |
| Authorized aliases | every alias declares a compatibility window and an authorizing migration contract; an unauthorized alias cannot be added |
| Identifier location | legacy identifiers appear only in the registry and the legacy inventory; the scrub scan fails on any other occurrence |
| Durable identifiers unchanged | no durable identifier is rewritten by this slice, proven by comparing the generated set against the `R0-13` inventory |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements, the `R0-13` identifier inventory,
`docs/product-plan/reference/legacy-inventory.md` and the structural migration
map. `.automonique/dev/guides/naming.md` states the three enforced rules this
contract mechanizes: one runtime owner for canonical and compatibility names,
compatibility entry points as forwarding or codec boundaries without duplicate
domain behavior, and no rename of a durable identifier or compatibility surface
without an explicit migration contract. Record the generated one-owner table,
the conflict case matrix and the count of aliases with and without an
authorizing contract.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, an alias not
generated from the registry, an alias carrying behavior the canonical path
lacks, a precedence rule resolving a canonical/alias conflict, a deprecation
signalled only as a log line, an entry resolving to two runtime owners, an
alias without an authorizing migration contract, a legacy identifier appearing
outside the registry and the legacy inventory, any rewrite of a durable
identifier, a licence-boundary violation, a forbidden clean-room input, or any
path outside the lease.
