## Objective

Define the durable vocabulary for work that starts without a person present:
canonical schedules that a natural-language expression must round-trip into,
occurrence keys that make duplicate firing impossible across reload, goals with
their completion contract and closed verdict set, waits bound to durable
conditions, fenced board claims, inbound trigger routes with verification and
replay windows, and notification delivery policy.

This slice defines values, canonicalization and verdict rules only. It runs no
scheduler, fires nothing, holds no lease, verifies no webhook signature,
delivers no notification and calls no model. Its central obligation is that
creating a schedule is never blanket authority for future arbitrary effects.

## Automation and goal contract

- A schedule is stored only in canonical form: a one-shot instant, a fixed
  duration, or a five-field cron expression with an explicit timezone and DST
  policy. A natural-language expression is *parsed into* a canonical schedule
  and returned with future example occurrences for review; it is never stored
  as prose and never scheduled directly. An ambiguous expression is a typed
  parse refusal, not a best guess.
- Canonicalization round-trips: parsing a canonical schedule's own rendering
  yields an identical schedule, and equal schedules render identically, so a
  review shown to an operator is the schedule that will run.
- Every occurrence carries a trigger occurrence key derived from the automation
  identity and the canonical fire instant. Two firings with the same key are
  the same occurrence — the type makes a duplicate detectable without
  coordination, so failover, clock recovery or a replayed tick cannot enqueue
  duplicate work.
- An automation revision is immutable and carries owner, tenant, enabled state,
  schedule, prompt or workflow reference, optional skills, profile, provider and
  model, workspace and context references, sandbox and budget, delivery targets
  and concurrency or overlap policy. Editing requires an expected revision, so
  a concurrent edit conflicts rather than overwriting.
- Unattended effect authority is explicit. An automation declares its
  pre-approved scope; an effect outside that scope is representable only as an
  approval request, never as a completed action. A no-agent script job and an
  agent job carry identical identity, sandbox and outbox obligations — the
  types do not offer a cheaper path for the one that skips the model.
- A `Goal` carries owner, objective text, an explicit completion contract,
  criteria or subgoals, budget, deadline, policy, active session or work-graph
  reference and status. After each turn the verdict is exactly one of
  `continue`, `complete`, `wait`, `blocked` or `budget_exhausted`, each carrying
  its evidence. A verdict without evidence is unrepresentable.
- Completion cannot rest on prose when the completion contract required tests,
  artifacts or receipts: a `complete` verdict whose contract demands artifact
  evidence and carries none does not typecheck. This is the rule that stops a
  persuasive summary from closing a goal.
- Wait conditions reference durable timers, run identities, connector events or
  monitored patterns — never an unbounded free-text label. A wake resolves an
  exact goal, job or session context; resuming from a text label alone is
  unrepresentable.
- A trigger route declares stable identity and path, tenant and service actor,
  allowed event types, verification method with replay window, payload and
  header limits, declarative filters, an optional sandboxed transform or typed
  template, its destination and idempotency extraction. Direct delivery
  bypasses the model but not destination authorization, outbox receipts or
  content limits.
- Board claims are fenced by an epoch and are hard authorization boundaries.
  Labels carry no authority; a type that treats a label as a tenancy control is
  not representable. Failure thresholds are declared and lead to a blocked
  state rather than unbounded retry.

## Verification contract

| Check | Expected |
|---|---|
| Canonical storage | only canonical schedules are storable; prose is unrepresentable; an ambiguous expression yields a typed parse refusal rather than a guess |
| Round-trip | parsing a canonical rendering yields an identical schedule and equal schedules render identically, proven over a fixture corpus including DST boundaries |
| Occurrence idempotency | the same automation and canonical instant yield the same occurrence key; duplicate ticks are detectable without coordination |
| Revision immutability | an automation revision is immutable; editing requires an expected revision and a stale edit conflicts rather than overwriting |
| Scope authority | an effect outside declared pre-approved scope is representable only as an approval request; no path yields a completed unattended effect |
| Job parity | no-agent and agent jobs carry identical identity, sandbox and outbox obligations, proven by a shared type path |
| Verdict closure | the verdict set is closed and exhaustive; every verdict carries evidence; a verdict without evidence is unrepresentable |
| Evidence-bound completion | a `complete` verdict lacking the artifact, test or receipt evidence its contract requires fails to typecheck |
| Wait resolution | wait conditions reference durable timers, runs, connector events or patterns; resuming from a free-text label alone is unrepresentable |
| Trigger routes | verification method, replay window, limits, filters, destination and idempotency extraction are required; direct delivery still carries destination authorization and receipts |
| Fenced claims | board claims carry an epoch; labels cannot serve as tenancy controls; failure thresholds block rather than retry unboundedly |
| Quality | workspace tests, strict Clippy and formatting pass offline with no new allowance, network access, runtime dependency or lockfile drift |

## Compatibility and evidence

Use only the permitted product requirements and synthetic fixtures.
`docs/product-plan/requirements/automation-goals-and-triggers.md` § Durable
automations, § Persistent goals, § Work boards and dispatch and § Inbound
webhook subscriptions, together with
`docs/product-plan/requirements/state-and-protocols.md` § Automations, goals and
inbound triggers, are the sources. Record the schedule round-trip corpus
results including DST transitions, the occurrence-key collision property test,
and the verdict matrix with one covering case per outcome. Self-improvement
goal origins are named in the requirement but are governed by the frozen
self-hosting items; this slice defines the general goal vocabulary and records
that restriction rather than implementing it.

## Stop conditions

Stop on any need for a new dependency or `Cargo.lock` change, a stored prose
schedule, an ambiguous expression resolved by guessing, a schedule that does
not round-trip, an occurrence key that permits duplicate firing, a mutable
automation revision, an edit without an expected revision, an unattended effect
outside declared scope, a no-agent job with weaker obligations than an agent
job, an open-ended verdict set, a verdict without evidence, a `complete` verdict
without the evidence its contract requires, a wake resolved from a text label,
a trigger route missing verification or limits, an unfenced board claim, a
label used as a tenancy control, a network or scheduler call, a licence-boundary
violation, a forbidden clean-room input, or any path outside the lease.
