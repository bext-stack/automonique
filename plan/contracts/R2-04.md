## Objective

Add one private, versioned Unix control endpoint for an R2-03 attempt spool. It
authenticates kernel peer credentials before reading a request, serves bounded
`inspect`, cursor-based `subscribe` and read-only `heartbeat` operations, and
delivers an internal-service-admitted, durably idempotent cancel request to the exact R2-06
descendant-complete cancellation service. A cancel response says only whether
the request was delivered or already delivered; process exit and terminal state
remain separate evidence.

The endpoint is an observation and protocol boundary. It does not launch or
adopt a process, read provider sockets, resolve credentials/workspaces/artifacts,
renew a durable lease, classify provider health, commit daemon business state,
or interpret disconnect as cancellation.

## Endpoint contract

### Dependency and ownership

- R2-03 supplies verified durable manifest/status facts and bounded cursor
  pages. The server consumes an already-created or already-recovered read-only
  observer; control requests never invoke recovery or parse spool files through
  a second representation. Any recovery-time status publication belongs solely
  to R2-03.
- R1-04 `PeerCredential`, `PeerPolicy`, `Admission` and entry rules are reused.
  The runner adds a path dependency on the existing workspace
  `automonique-policy` crate; only the runner dependency list may change in
  `Cargo.lock`, with no registry package/version delta.
- R2-06 supplies one server-held, non-cloneable host cancellation dispatcher.
  It registers target-bound descendant-complete cancellation capabilities, and
  its only mutation accepts the R2-06-owned non-wire `AttemptCancelRequest`
  carrying the R2-06-owned exact attempt target, R1-25 `RequestRef` and observed
  sequence. One host-wide durable ledger, owned and recovered by R2-06 and
  shared by all target registrations, deduplicates `RequestRef`; exact replay returns `already_delivered`, while reuse with a
  different target or observed sequence conflicts. A caller cannot construct
  the dispatcher, target capability or ledger entry from a receipt, token or
  message body.
- One host server owns one fixed `control.sock` and at most 128 attempt bindings.
  Attempt lifetime registers one; session lifetime may register/unregister
  multiple through an in-process host-owned registration capability that is
  private to the server construction module and absent from the wire. Each
  binding owns an R2-03 observer and a registration in that R2-06 dispatcher.
  Registration is linearized: an already-present attempt ID, any changed target
  coordinate or a 129th binding refuses without replacement. Unregister
  requires exact equality of the full target. An admitted worker snapshots an
  immutable observer plus target-bound cancellation handle while holding the
  registry guard; unregister prevents new snapshots but cannot retarget or
  invalidate an in-flight operation. Re-registration waits until every old
  snapshot is dropped, so an attempt ID cannot cross-route during churn.
- The server owns its listener and workers. Dropping or shutting it down closes
  clients and removes only the socket inode it created; it never cancels the run.

### Filesystem and socket identity

- Configuration accepts a caller-supplied absolute host-runtime directory and
  fully validates it; successful validation grants no claim that a host registry
  selected it. The final socket
  component is fixed as `control.sock` and Unix path-length overflow refuses
  before a filesystem call.
- Before bind, each existing directory component is inspected without following
  symlinks. The host directory must be a directory, effective-UID-owned and
  exact mode `0700`; group/world-writable parents, symlink components, wrong
  owner, wrong mode and noncanonical path spelling refuse.
- The threat boundary excludes a malicious same-UID process racing path
  components; mode and ownership do not protect from the same UID. The server
  revalidates after bind and during cleanup, but makes no stronger race-free
  pathname claim than the available filesystem API supports.
- If `control.sock` is absent, bind proceeds. If present, `lstat` must show a
  socket owned by the effective UID with exact mode `0600` and link count one.
  A bounded nonblocking connect is polled for at most exactly 250 milliseconds,
  then `SO_ERROR` is read: zero means active and refuses. Only
  `SO_ERROR == ECONNREFUSED` is stale: the server
  re-`lstat`s exact device/inode/type/owner/mode/link-count equality immediately
  before unlink.
  Permission, timeout, unexpected error, symlink or metadata drift is ambiguous
  and refuses without unlink.
- Bind occurs under the private `0700` directory, then the socket is set to exact
  mode `0600` and revalidated as socket/effective-UID/device/inode/mode. The
  listener and every accepted stream are close-on-exec and nonblocking at the
  listener boundary. A post-bind failure invokes the same identity-checked RAII
  cleanup.
- Cleanup captures the created socket device/inode. It attempts unlink only if
  current named entry is still that exact owned `0600` socket. Replacing the
  pathname and having that replacement observed by the final `lstat` prevents
  cleanup from deleting it. The final check-to-unlink same-UID race remains
  outside the stated threat boundary and is not claimed closed.

### Authentication before parsing

- Immediately after `accept`, the transport obtains Linux `SO_PEERCRED` through
  the existing safe `nix` dependency by enabling the already-locked package's
  `socket` feature; bounded deadlines enable its `poll` feature. No
  package/version changes. The
  transport constructs the R1-04 credential. No
  prefix, payload byte or request deadline is read first.
- The runner must have a non-root effective UID. Server construction derives
  one immutable `PeerPolicy` admitting exactly that UID; no public config or
  request may select or widen the admitted set. Missing credentials, any other
  UID and root close the stream with zero parsed requests. GID and PID are
  diagnostic only and never change admission.
- Successful peer admission is the reviewed internal-service transport and
  disclosure boundary for bounded status and exact spool records, and the
  transport delegation boundary for attempt-cancel delivery. It is not a user
  role, tenant authorization or R1-13 Decision. The daemon must apply tenant
  and deny-by-default operator policy before it uses this internal socket.
  This deliberate boundary is recorded in
  `plan/owner-decisions/2026-08-12-r2-04-internal-service-boundary.md`; it does
  not widen R1-04's narrower claim. Request fields cannot assert UID, actor,
  role, admission or policy evidence.
- Peer admission alone is insufficient for cancellation: the exact target must select a
  registered nonfabricable R2-06 service, and its durable idempotency decision
  controls delivery. R1-04 admission is never converted into an R1-13 Decision.

## Wire contract

### Framing and common grammar

- Protocol is exactly `automonique.runner`, major version JSON integer `1`.
  Frames use protocol `encode_frame`/`decode_frame`: four-byte big-endian length
  followed by canonical UTF-8 JSON, never newline framing.
- Request payload ceiling is exactly 65,536; response payload ceiling is exactly
  2,097,152. A zero or greater-than-65,536 request prefix refuses before payload allocation.
  Exact 65,536 reaches canonical/schema validation (the closed request grammar
  itself is smaller); 65,537 refuses at framing. Largest valid request succeeds.
  Every valid response, including one maximum event record, fits 2 MiB.
- Each connection carries exactly one request and at most one response, then
  closes. Prefix/body read and complete response write each have an exact
  two-second deadline. Partial prefix, partial body and write timeout close the
  observer only and never affect spool/run state.
- Every object is closed: exact keys, JSON types and mandatory nulls. Canonical
  parser rules refuse whitespace, reordered keys, duplicate/unknown/missing
  keys, alternate escapes, trailing bytes and noncanonical numbers. Unsigned
  quantities are canonical decimal strings `0|[1-9][0-9]{0,19}` to preserve the
  full `u64` domain.
- `S` means the exact bounded spelling accepted by its owning typed constructor;
  `U` means the decimal string above; `D` means canonical lowercase SHA-256.
  Errors carry only static field/category data and never echo request, payload,
  socket path or event text.

Every request has exactly:

```text
{"body":RequestBody,"kind":"inspect"|"subscribe"|"heartbeat"|"cancel",
 "protocol":"automonique.runner","request_id":S,"version":1}
```

`request_id` uses protocol `RequestId`. The kind and body variant must agree.
Every response reuses the normal five-key protocol `Message` envelope exactly:

```text
{"body":ResponseBody,"kind":"status"|"subscription_page"|
 "heartbeat_observed"|"cancel_result"|"refused",
 "protocol":"automonique.runner","request_id":S,"version":1}
```

It repeats the exact admitted request ID. Success/refusal is expressed by the
closed kind, not an extra envelope key. A parseable admitted request receives
at most one bounded response; an unauthenticated or malformed request may close
without a response. A refusal response contains only
`{"category":E,"retryable":false}`. `E` is exactly
`field_invalid|target_unknown|target_mismatch|cursor_ahead|resync_required|
cancel_conflict|cancel_unavailable|internal`;
Refusal precedence is phased exactly: peer admission before any byte read;
canonical envelope, closed schema and every typed field construction;
attempt-ID lookup; full target equality; then operation-specific cursor or
cancellation state. A failure in a phase prevents every later phase. Peer
refusal and malformed messages with no canonical request ID close without a
response; the remaining named categories follow the phase order above.
`target_unknown` means no registered binding has the supplied attempt ID;
`target_mismatch` means that attempt exists but another target coordinate
differs. `cancel_unavailable` is returned only when the selected R2-06
dispatcher reports that the target is terminal, reconciling or shutting down
and accepted no signal. The 9th live connection and a worker-permit race close
before parsing rather than inventing a request-correlated `server_busy` body.
`field_invalid` is reserved for a canonical envelope/body whose typed field
constructor or cross-field rule refuses.
After canonical envelope/body and typed fields validate, the server looks up
the attempt ID, compares every remaining target coordinate, and only then
evaluates cursor or cancellation state. Invalid spelling therefore cannot probe
attempt existence.

Every request operation carries the same exact target:

```text
Target={"attempt_id":S,"host_id":S,"run_id":S,
 "run_spec_digest":D,"work_id":S}
```

Every success body repeats this target. All five coordinates must equal one
registered server-held binding; run ID alone never selects an attempt.

### Inspect

Request body:

```text
{"target":Target}
```

The run must equal the bound spool run. Success kind is `status` with body:

```text
{"backend_id":S,"host_lifetime":"attempt"|"session","last_sequence":U,
 "spool_state":"empty"|"nonterminal"|"terminal"|
               "reconciliation_required",
 "target":Target,
 "terminal_outcome":null|"completed"|"failed"|"cancelled"|
                         "timed_out"|"lost"}
```

The outcome is non-null exactly for terminal. This is one consistent R2-03
status snapshot plus immutable RunSpec projections; it contains no argv,
environment, prompt/reference, event/raw payload, path, provider session or
credential descriptor/value.

### Subscribe

Request body:

```text
{"after":U,"stream":"events"|"stdout"|"stderr","target":Target}
```

`after` is always the R2-03 event/chunk sequence, never a raw byte offset. The
server asks the R2-03 API for exactly one record using 524,288 bytes for events
or 196,608 for raw streams. Thus no cursor advances past omitted content.

Success kind is `subscription_page`:

```text
{"more":bool,"next_cursor":U,"record":null|RecordProjection,
 "stream":"events"|"stdout"|"stderr","target":Target}
```

Event projection:

```text
{"chain_digest":D,"encoded_bytes":U,"record_hex_chunks":[H32],
 "sequence":U}
```

Raw projection:

```text
{"chain_digest":D,"encoded_bytes":U,"record_hex_chunks":[H32],
 "offset_end":U,"offset_start":U,"sequence":U,
 "stream":"stdout"|"stderr"}
```

`H32` is the R2-03 canonical lowercase even hex fragment decoding to at most
32,768 bytes. Every nonfinal fragment decodes to exactly 32,768 bytes and the
final fragment to 1..=32,768. A non-null event record has 1..=16 fragments and
a non-null raw record 1..=6; `[]` is therefore invalid for a record. The server
decodes the exact R2-03 record and verifies that every duplicated sequence,
digest, offset, stream and target coordinate equals the record before response
construction. All record bytes are returned losslessly; there is no descriptor-only observation
and no cursor advances past unhandled bytes. `record` is null exactly when no
later record exists, in which case `next_cursor` equals `after` and `more` is
false. With a record, `next_cursor` is its sequence and `more` is the exact
R2-03 continuation fact. Cursor
zero begins retained history, middle resumes strictly later, last is empty,
ahead returns `cursor_ahead`; future retention gap returns `resync_required`,
never a silent suffix.

Subscribe is bounded polling, not an unbounded pushed stream. Reconnect from the
last handled cursor yields exactly the next page. Disconnect, response timeout
and client-side iterator cancellation affect only that observer and never the
spool, provider or run cancellation token.

### Heartbeat

Request body:

```text
{"observed_sequence":U,"target":Target}
```

The run must match and an observed sequence ahead of current status refuses.
Success kind is `heartbeat_observed`:

```text
{"last_sequence":U,"server_started_at_millis":I,
 "spool_state":"empty"|"nonterminal"|"terminal"|
               "reconciliation_required",
 "target":Target,"uptime_millis":U}
```

`I` is canonical signed `i64` decimal time. `uptime_millis` is monotonic since
this server instance started and saturating is forbidden; overflow shuts the
endpoint down with a typed internal failure. Repeated heartbeat requests append
nothing, change no status/cursor/lease and do not prove provider/session/process
health. Restart resets uptime and may repeat wall-clock start time; neither is
an authentication or durable instance identifier.

### Cancel

R1-25 `CancelScope` names turn, tool and queue interactions, not the complete
attempt descendant boundary. The wire therefore uses a distinct closed cancel
body rather than relabeling one of those scopes. Request body:

```text
{"observed_sequence":U,"request_ref":S,"target":Target}
```

`request_ref` reuses the bounded R1-25 `RequestRef`; scope is structurally the
exact attempt in `Target`, with no caller-selected reason or scope.
`observed_sequence` is storage evidence, not a business revision:
ahead refuses, while a behind value is allowed and recorded by R2-06. Exact
target and peer admission losslessly map every field into the R2-06-owned
`AttemptCancelRequest` and invoke the selected service; neither wire type can be
substituted for the service type. R2-04 validates the R2-06 target field by
field against the registered R2-03/RunSpec binding facts. Response
`cancel_result` is exactly
`{"disposition":"delivered"|"already_delivered","request_ref":S,
"target":Target}`. Same reference with a different target or observed sequence
conflicts.
Delivery does not mean the process exited or terminal status exists.
Ledger lookup precedes current target availability: an exact durable replay
returns `already_delivered` even after the target becomes terminal,
reconciling or shutting down; altered reuse conflicts before that availability
check. Only a previously unseen reference may return `cancel_unavailable`.

## Concurrency, lifecycle and resource bounds

- At most 8 accepted clients are live. Admission reserves a permit before a
  worker is created; excess connections close without parsing. A worker owns at
  most one 65,536-byte request buffer, one 2,097,152-byte response buffer, one
  R2-03 source page (at most 524,288 bytes), one request AST bounded by its
  input and a configured 256-KiB stack. Aggregate logical ceilings are 524,288
  request-buffer bytes, 16,777,216 response-buffer bytes, 4,194,304 source-page
  bytes and 2,097,152 stack bytes. Parser/projection allocations use checked
  lengths and an 8-MiB per-worker logical allocation budget before reserve. The
  report separately records observed allocator, RSS, thread and socket peaks
  and never calls logical byte arithmetic total process memory.
- A bounded thread-per-connection implementation is permitted only with the 8
  permits, exact deadlines and guaranteed joining. No unbounded queue or idle
  thread exists. The nonblocking accept loop checks shutdown at least every 50
  milliseconds and malformed/slow peers cannot stop it.
- Response canonical size is preflighted before final allocation; a projection
  beyond 2 MiB is an internal invariant refusal and never partially written or
  silently truncated.
- Shutdown stops accepts, closes live streams, joins every worker and removes
  only the created socket inode. It neither appends a spool event nor cancels
  the run. FD/thread counts return to baseline after normal and hostile clients.
- Restart consumes already-recovered R2-03 observers, creates a new socket inode
  and serves verified status/cursors. Nonterminal recovery
  remains `reconciliation_required`; the socket does not invent running state,
  provider liveness, cancel receipts or discoverability beyond the containing
  host registry.
- Spool status/page snapshots are copied under one short synchronization guard;
  socket reads/writes and response encoding occur after releasing it. A slow or
  hostile observer therefore cannot block the single spool writer.

## Compatibility and non-goals

This is a fresh private `automonique.runner` v1 endpoint. It does not emit
`legacy.runner`, TCP, HTTP, WebSocket, SSE or newline-delimited frames. It is a
bounded direct host observer for the later daemon/SDK surfaces, not the public
operator API. Polling subscription is intentional until a bounded notification
primitive exists; a client resumes by cursor and never treats disconnect as a
run mutation.

R2-06 owns descendant-complete cancellation/timeout semantics and durable
idempotency; R2-04 transports an internal same-effective-UID service request to
that capability. The daemon remains responsible for binding an authenticated
operator to immutable deny-by-default `run:cancel` evidence. Direct untrusted
operator clients are not admitted to this internal endpoint.
The same-UID process boundary is not a confidentiality or integrity defense
against `/proc`, a debugger, direct access to the mode-`0600` spool, signals or
same-UID pathname races; those capabilities are outside this endpoint's threat
model rather than silently claimed closed.

## Stop conditions

Stop on parsing before kernel credentials and peer admission; body-supplied
identity/role/admission; caller-selected peer policy, wildcard or root peer
access; peer admission represented as role/tenant authorization; cancel without
exact peer admission, target, typed request and R2-06 service; cancel response
claiming exit; disconnect-as-cancel;
unbounded frame/client/thread/queue/page/allocation; request over 65,536 or
response over 2,097,152 bytes; cursor advancing past omitted data; cursor ahead/gap silently succeeding; pushed
subscription without bounded backpressure; heartbeat mutating state or claiming
provider/process health; arbitrary socket path; unlink without exact inode
revalidation; symlink/wrong-owner/wrong-mode acceptance; path/socket/payload in
errors; FD without CLOEXEC; cleanup deleting a replacement; runner/spool/provider
mutation; launch/adoption/network/credential/workspace/artifact activity; a new
registry package/version or lock drift beyond the reviewed runner-to-policy
path edge; unsafe/lint weakening; private-archive/network access; licence
crossing; out-of-lease edit; or a required-check failure outside scope.
