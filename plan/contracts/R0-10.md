## Objective

Prove the baseline backup and restore path by drill: take a consistent backup,
restore it to a clean disposable host, and measure the result against the
declared initial recovery point and recovery time objectives. The drill
establishes that the objectives are real measurements rather than aspirations
before any self-hosting work depends on them.

The drill operates on synthetic fixture state it creates itself. It never
backs up or restores a production system and holds no production credential.

## Drill contract

- The drill asserts before starting that its source and target are disposable
  fixture state, not a production system or the live repository, and refuses to
  run rather than proceeding when it cannot make that assertion.
- Consistency is proven, not assumed: the backup is taken such that a restore
  yields a single coherent point in time, and the drill demonstrates the
  restored state is internally consistent rather than merely present.
- The target is a clean host: the restore runs against state that carries
  nothing from the source beyond the backup artifact itself, so a hidden
  dependency on the source cannot silently satisfy the drill.
- For this baseline, that clean host may be a fresh same-kernel isolation
  boundary on the same class of host. It is not a VM or hostile-kernel
  boundary. The source fixture and live repository are inaccessible, the
  target begins empty, and only the backup artifact crosses from source to
  target. Clean-side runtime and release inputs are declared dependencies.
- RPO and RTO are measured and reported as numbers with their units, compared
  against the declared initial objectives. Missing a declared objective is a
  recorded finding with the measured value, never a silent pass and never a
  retroactive loosening of the objective.
- The synthetic backup cadence and injected-loss offset are fixed before
  execution. RPO is the elapsed duration between the recovered watermark and
  the newest durable fixture state at loss. RTO starts immediately before
  creation of the disposable host boundary and ends only after restore
  consistency, all applicable dependency verification and
  disconnected-recovery startup succeed. These are baseline-boundary results,
  not production-readiness evidence.
- The restore dependency list from `R0-09` is consumed rather than reinvented.
  A dependency the drill discovers but the inventory lacks is reported back as
  a finding.
- The consumer accepts only
  `plan/inventory/surface/restore-dependencies.json`, schema
  `automonique.restore-dependencies/v1`, produced for `R0-10`, and verifies its
  bytes re-derive from R0-09's source inventory. It records every ordered
  position as `exercised`, `verified-disabled`, `not-applicable` with a
  source-backed reason, or `required-but-not-exercised`. Any
  `required-but-not-exercised` position blocks completion. An enablement gate
  is satisfied by proving it remains closed, never by enabling a transport or
  provider.
- The drill is idempotent and leaves no residue: rerunning reproduces the
  outcomes, and fixture state is cleaned up after both success and failure.

## Verification contract

| Check | Expected |
|---|---|
| Safety refusal | the drill refuses to start unless source and target are provably disposable fixture state |
| Backup consistency | the backup yields one coherent point in time and the restored state is shown to be internally consistent |
| Clean-host restore | the restore succeeds against a target carrying nothing from the source but the backup artifact |
| Objective measurement | RPO and RTO are measured with units and compared to the declared objectives; a miss is a recorded finding with its measured value |
| Dependency agreement | the `R0-09` restore dependency list is consumed; any dependency it lacks is reported as a finding |
| Rerun hygiene | a second run reproduces every outcome and leaves no fixture residue after success or failure |
| Quality | the drill runs offline with no network access, no production credential and no new runtime dependency |

For the Quality row, `no new runtime dependency` means no prerequisite absent
from the admitted-base environment becomes required and no install or network
fetch occurs. An isolation executable already declared at the admitted base may
be reused only when its resolved path and version are recorded, absence refuses
the run without a weaker fallback, and invocation uses exact arguments, no
shell, a cleared environment, and no inherited credential or network authority.

## Compatibility and evidence

Record the measured RPO and RTO with units, the declared objectives they are
compared against, the restore dependency list actually used, and any
dependency discovered but missing from `R0-09`. Report the drill as evidence
for the baseline recovery boundary without claiming production readiness. An
unrun scenario is `null` with a reason, never a pass.

## Stop conditions

Stop on any inability to prove source and target are disposable, a scenario
that would read or write a production system or the live repository, a restore
that silently depends on state the backup did not carry, an unmeasured or
retroactively loosened objective, a declared objective missed and reported as a
pass, any reachable production credential, residue left after a run, a
licence-boundary violation, or any path outside the lease.
